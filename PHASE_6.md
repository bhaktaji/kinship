# Phase 6 — Load, resilience and production-readiness evidence

Status: **complete for the local single-host stack; multi-host and 2-hour soak are
not executed.** Gate A (security remediation) was approved before this phase.
Every figure below comes from a file in `perf/results/`; the raw method and
reproduction commands are in `docs/perf/baseline.md`.

## 1. What changed in this phase

Only what a measurement justified:

| Change | Why |
|---|---|
| Micrometer + Prometheus registry, `X-Metrics-Token`-gated endpoints | Needed to attribute load results to pool/lock/GC rather than guess |
| `CountReconciliationJob` (nightly, repairs `events.confirmed_count`) | Seat counter had no self-healing path |
| Hikari pool 10 → 20 | Measured: at 150 concurrent `/v1/users/me`, pool 10 delivered 35.8 rps with 86 client failures; pool 20 delivered 262 rps with none |
| Redis command/connect timeout 2 s → 300 ms | Measured: a Redis stop added 7.26 s to discovery and hung login; after the change discovery answers in 1.04 s and login fails cleanly with 503 |

No Kafka, no Kubernetes, no sharding, no read replica, no second database. The
matching worker still drains serially (bounded at 500 candidates), which is far
inside its 5,000-user target.

## 2. Environment and dataset

Windows 11 host, Docker Desktop 29.9.2, one WSL VM with 3.68 GiB. Containers:
`kinship-api-1` (Spring Boot 3.3.13, Java 21 virtual threads), PostGIS 16-3.4,
Redis 7 (no persistence), Next.js 15.5.29. Load generated by `grafana/k6` inside
the compose network plus two Node probes. 5,271 users, 102 groups, 58 messages,
41 RSVPs, 12 match jobs; 50 deterministic load accounts.

## 3. Results

### 3.1 Staged load (`perf/k6/01`–`04`)

| Stage | VUs | Duration | Requests | Throughput | p95 | Failures |
|---|---|---|---|---|---|---|
| Smoke | 5 | 30 s | 275 | 9/s | 42.5 ms | 0 % |
| Baseline | 20 | 3 min | 13,976 | 77.5/s | 7.0 ms | **0 %** |
| Moderate | 50 | 5 min | 95,360 | 317.6/s | 6.2 ms | **18.3 %** |
| Stress | 10→200 | 7 min | 409,320 | 974/s | 48.1 ms | **40.2 %** |

The 18.3 % and 40.2 % are **not** capacity failures. Discovery is limited to
120 requests/minute per user. The baseline stage runs at ~116/min per user and
passes; the 50-VU stage runs at ~380/min per user and the excess is rejected.

Confirmed directly with a 200-request burst from one account at concurrency 40:

```
discovery-burst: statuses={"200":120,"429":61,"ERR:TypeError":19}
```

The first 120 requests succeed, every later one is 429 — exactly the configured
window. (The 19 transport errors are client-side `fetch` failures from the Node
process under a 40-way burst, not API responses.)

### 3.5 Failure injection (`perf/chaos.sh`)

| Injection | Behaviour | Recovery |
|---|---|---|
| Redis stopped | `/readyz` 503 (0.33 s), login 503, ticket 503, discovery 200 in 1.04 s (cache fails open), message 201 (persisted, live publish lost) | `/readyz` 200 in 2 s; no API restart |
| PostgreSQL stopped | `/readyz` 503 (3.1 s), `/healthz` 200, discovery 200 in 0.22 s (Redis), login/message 503, container `running`, `restarts=0` | `/readyz` 200 in 4 s; counts unchanged |
| Stale `RUNNING` job + API restart | job swept to `FAILED / JOB_TIMEOUT` | new jobs process normally |

Data after all injections: users 5,271, groups 102, messages 58 — unchanged.

### 3.6 Backup and restore

`pg_dump -Fc` → 520,488 bytes in 18 s; restore into a scratch database in 60 s;
all row counts identical (users 5,271, groups 102, messages 58, RSVPs 41, jobs 12,
latest message sequence 6); scratch database dropped, live database untouched.
There is still no schedule, no off-host copy and no PITR.

## 4. Failures found and what was done

1. **Redis outage amplified latency (7.26 s discovery, hung login).** Fixed by
   lowering Redis connect/command timeouts to 300 ms; re-measured at 1.04 s and a
   clean 503.
2. **Pool saturation at high concurrency.** `CannotCreateTransactionException` →
   503 was observed with pool 10. A direct comparison at 150 concurrent
   `/v1/users/me` gave 35.8 rps with 86 client failures (pool 10) versus 262 rps
   with none (pool 20). Pool raised to 20 on that evidence.
3. **Stale `RUNNING` match job after a crash.** `recoverStale()` moves it to
   `FAILED / JOB_TIMEOUT` on the first sweep; verified by inserting a 12-minute-old
   job and restarting the API.
4. **18.3 % "failures" at 50 VUs.** Investigated as capacity; direct probe showed
   they are 429s from the 120/min per-user limiter. No code change — the limiter
   is behaving as configured, and the load model (not the API) was miscalibrated.
5. **Stress-stage measurement is generator-bound.** With 200 VUs on a 3.68 GiB
   host shared with k6, throughput fell to 125 rps and p95 rose to 2.8 s while
   failures dropped to 6.5 %; a second run with the same script produced the
   opposite trade-off (974 rps, 40 % rejected). Treat the 7-minute stage as a
   saturation signal, not a capacity number.

## 5. Known gaps

- No per-user/per-group socket cap and no slow-consumer queue (L7).
- Single host, single database, no PITR; backup is manual and on-host.
- No alerting; metrics are exposed but nobody watches them.
- 2-hour soak not run; multi-host and proxy/TLS behaviour not tested.
- Rate limiter is per-user and per-minute with a fixed window; legitimate heavy
  clients can hit it (by design, but it is a product decision to revisit).
- Java CVE scan outstanding.
