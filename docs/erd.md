# Entity Relationship Diagram (ERD)
## Recurring-Activity Friendship Platform

Version: 1.1 | Status: Reviewed for implementation (Phase 0) | Applies to: PostgreSQL 16 + PostGIS 3.4

---

## 1. Scope

This ERD covers the **MVP schema** implemented by Flyway migrations
(`V1__schema.sql`, `V2__indexes.sql`). Tables for notifications, attendance
check-in, reports/moderation, and payments are deliberately **not** modelled in
the MVP (see `hld.md` §12).

Storage rules:

- All identifiers are `uuid` generated by the application (Java `UUID.randomUUID()`).
- All timestamps are `timestamptz` stored in UTC. Local rendering uses `users.timezone`.
- Geography columns are `geography(Point, 4326)`; distance queries return metres.
- Enumerations are stored as `text` with `CHECK` constraints (no PostgreSQL enum types, to keep migrations simple).

## 3. Constraints, Uniqueness and Invariants

| Table | Constraint | Rule |
|---|---|---|
| users | `UNIQUE (lower(email))` | Case-insensitive unique email |
| user_interests | `PRIMARY KEY (user_id, interest_id)` | One weight per interest |
| group_members | `PRIMARY KEY (group_id, user_id)` | One membership row per user/group |
| group_members | partial unique on `role='OWNER'` | Exactly one OWNER per group |
| groups | `max_members BETWEEN 2 AND 20` | Group size limit |
| event_series | `UNIQUE (group_id, title, starts_on)` | Prevents duplicate series creation retries |
| events | `UNIQUE (series_id, start_time)` | Idempotent occurrence generation (NULL series allowed for one-offs) |
| events | `CHECK (end_time > start_time)`, `capacity BETWEEN 1 AND 100` | Valid occurrence |
| rsvps | `PRIMARY KEY (event_id, user_id)` | One RSVP per user per occurrence |
| match_groups | `UNIQUE (job_id)` | One proposal per matching job (worker retry safety) |
| messages | `UNIQUE (group_id, sequence_id)` | Dense, gap-free-per-group ordering |
| messages | `UNIQUE (group_id, client_msg_id)` where not null | Send idempotency |
| match_jobs | partial unique `(user_id)` where status in ('QUEUED','RUNNING') | One active job per user |
| match_invitations | `UNIQUE (match_group_id, user_id)` | One invitation per user per proposal |

Derived values kept consistent in the same transaction:

- `events.confirmed_count` = number of `rsvps` with `status='GOING'`.
- `groups.last_message_seq` = highest allocated `messages.sequence_id` for the group.
- `match_groups.group_id` is non-null **iff** `match_groups.status='CONFIRMED'`.

Application-enforced rules (not expressible as simple constraints):

1. A user may only RSVP to an occurrence of a group where they are an `ACTIVE` member.
2. A group with `visibility='private'` is visible only to its members and pending invitees.
3. `event_series.capacity` defaults to `groups.max_members` and must be `>=` the number of `GOING` RSVPs at creation time.
4. `users.location` may be null (profile incomplete); such users are excluded from discovery and matching.

## 5. Relationship Notes

- **Activity vs group vs event.** An *activity* is a discoverable offering tied
  to a location (e.g. "Thursday evening bouldering"). A *group* is the small
  persistent circle that meets for that activity. An *event series* is the
  recurrence definition owned by a group; each *occurrence* is one dated event.
  Discovery cards are activity rows joined to the group that currently has space.
- **Match groups are proposals, not groups.** A `match_groups` row exists before
  any group; on quorum (4 accepted invitations) the application creates a real
  `groups` row and links it through `match_groups.group_id`.
- `match_groups.member_user_ids` is a `uuid[]` snapshot of the proposed members.
- **Message sequence** is allocated from `groups.last_message_seq` inside the
  insert transaction, so it survives Redis outages and process restarts.
- `events.activity_id` is optional and copied from the group's activity for
  reporting; the group remains the owner of the occurrence.

## 6. Deferred (Post-MVP) Tables

`notifications`, `attendance` (check-in), `reports` / `blocks`,
`payments`, `push_tokens`. They are intentionally absent to keep Phase 1
migrations small; no MVP endpoint depends on them.
